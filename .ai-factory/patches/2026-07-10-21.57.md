# Keep Mini App navigation safe and session reads singular

**Date:** 2026-07-10 21:57
**Files:** frontend/src/app/(miniapp)/layout.tsx, frontend/src/components/miniapp/MiniappSessionContext.tsx, frontend/src/components/miniapp/MiniappTabs.tsx, backend/internal/application/query/get_participants.go, backend/internal/infrastructure/http/handler/miniapp.go
**Severity:** high

## Problem

The fixed Mini App navigation reserved a hard-coded 96 px at the bottom of the
page while its actual height also includes the device safe-area inset. On iOS,
the final content could be hidden behind the navigation. The navigation and the
active screen also loaded `/api/miniapp/session` independently; that endpoint
loaded and ranked every participant just to find the current user's result.

## Root Cause

The layout did not share the same safe-area calculation as the fixed navigation.
Session ownership was split between two page-specific contexts, so the new
layout-level navigation had no shared source of session data. The session
handler reused a leaderboard query instead of the repository's targeted
`FindByUserAndEvent` capability.

## Solution

Use `calc(env(safe-area-inset-bottom) + 5rem)` as the Mini App content reserve.
Add `MiniappSessionProvider` at the shared layout level and use it from the
navigation, leaderboard, and gifts screens. Add a dedicated application query
for one participant by user and event, then use it in the session handler.
The handler logs the resolved own-result state with `[FIX]` without exposing
another participant's user ID.

## Prevention

- Fixed mobile controls and their content reserve must use the same safe-area
  formula.
- Shared layout data belongs in one provider rather than in route-specific
  providers.
- Do not reuse list-and-rank queries when a request needs only one participant;
  add a focused application query instead.
- Keep tests for the targeted user/event lookup and the session's own-result
  mapping.
