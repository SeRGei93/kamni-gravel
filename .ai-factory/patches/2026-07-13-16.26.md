# Criteria prize assignments and heart-rate time metric

**Date:** 2026-07-13 16:26
**Files:** backend/internal/application/query/prize_distribution_engine.go, backend/internal/application/dto/result.go, backend/internal/application/dto/participant.go, backend/internal/domain/entity/result.go, backend/internal/infrastructure/http/handler/participants.go, frontend/src/components/participants/participantColumns.tsx
**Severity:** high

## Problem

A participant who had already received a `criteria+place` prize was excluded
from a separate criteria-only prize. A criteria-only prize also stopped after
the fastest matching participant, even when the same criterion was assigned to
multiple participants. This made valid category prizes appear unassigned.

The participants table also lacked the requested derived value: elapsed time
in minutes multiplied by average heart rate.

## Root Cause

`assignNoPlaceGift` treated every no-place gift as a single slot and applied
`blockedByHigherPriority` indiscriminately. This conflated generic fallback
prizes with rewards for explicitly matched criteria. The derived heart-rate
metric existed only as raw elapsed seconds and average heart-rate values, with
no server-side value for paginated sorting.

## Solution

- Assign every eligible participant for a criteria-only gift, without applying
  the higher-priority blocker. Generic no-place gifts remain single-recipient
  and retain their fallback behaviour.
- Add `[FIX:criteria-prize]` distribution diagnostics with the number of
  criteria assignments.
- Add the read-only `heart_rate_time_product` API field, calculate it in the
  domain from elapsed seconds and average heart rate, expose a visible sortable
  `ЧСС × время` table column, and keep missing inputs empty.
- Add regression coverage for multi-recipient criteria gifts, the
  `criteria+place` then criteria-only sequence, domain calculation, DTO list
  mapping, server-side sorting, and the frontend column registry/formatting.

## Prevention

- Keep generic fallback capacity separate from explicitly matched criteria in
  prize-distribution changes.
- Add a test for each cross-priority combination whenever a new prize rule is
  introduced.
- Add derived table metrics to both the API DTO and the server-side sorter so
  pagination cannot produce incorrect ordering.
