# Move participant notifications out of the HTTP request

**Date:** 2026-07-13 18:48
**Files:** backend/internal/application/command/participant_notification_jobs.go, backend/internal/application/command/send_participant_notifications.go, backend/internal/infrastructure/http/handler/participant_notifications.go, backend/internal/infrastructure/http/server.go, frontend/src/api/participantNotifications.ts, frontend/src/app/(dashboard)/participant-notifications/page.tsx
**Severity:** high

## Problem

An administrator notification was delivered synchronously by the HTTP handler.
The server has a 15-second write timeout, while the delivery loop intentionally
waits between recipients and also performs Telegram network calls. A large
audience could therefore receive only a partial broadcast before the browser
request timed out. Retrying from the UI would duplicate messages for people who
had already received them.

## Root Cause

The HTTP response and the full Telegram delivery lifecycle were treated as one
operation. The rate-limit delay correctly protected Telegram, but it made the
request duration proportional to the number of selected recipients and ignored
the HTTP timeout budget.

## Solution

Added an in-memory FIFO `ParticipantNotificationJobManager` with one worker.
The protected POST endpoint validates and queues a job, returns `202 Accepted`
with its ID, and the frontend polls a new job-status endpoint. The worker owns
the existing sequential delivery loop, records queued/running/completed/failed
state, and logs lifecycle events using `[FIX:participant-notification-queue]`.
Server shutdown cancels the worker so a partially processed job is marked as
cancelled instead of reported as completed.

## Prevention

- Do not perform a rate-limited fan-out operation inside an HTTP request with a
  fixed write timeout.
- For admin broadcasts, return a job ID and expose explicit terminal status
  before allowing a retry.
- Keep one delivery worker per bot token unless a shared, rate-limit-aware queue
  is introduced.
- Cover queued-to-completed delivery and cancellation status with regression
  tests.
