# Serialize random gift recipient claims

**Date:** 2026-07-13 23:57
**Files:** backend/internal/domain/repository/gift.go, backend/internal/infrastructure/persistence/postgres/gift_repo.go, backend/internal/infrastructure/persistence/postgres/gift_repo_test.go
**Severity:** high

## Problem

Two administrator requests could concurrently select the same unawarded
participant for different gifts. Each request only compared and set its own
gift row, so both writes could succeed and give the participant two prizes.

## Root Cause

Candidate eligibility was checked before the write, while the repository
compare-and-set protected only `gifts.id`. There was no shared lock or
post-lock check for the selected participant, and the existing recipient index
is intentionally non-unique for ordinary manual assignments.

## Solution

`AssignRandomManualRecipient` now uses a transaction. It locks the target
gift and participant with `FOR UPDATE`, then performs a new-statement check
for an existing manual award before conditionally updating the gift. A second
random request for the same participant waits on the participant lock, sees
the first transaction's commit, and returns the existing conflict error.
Structured `[FIX:random-recipient-claim]` logs record transaction start,
success, rejection, and failure stages. The repository regression test
asserts the transactional lock/check/update sequence and the stale-candidate
conflict.

## Prevention

- Treat candidate lists as preflight data, not as a concurrency guarantee.
- When a mutation must claim a shared resource, lock that resource and
  revalidate the invariant in a later transaction statement.
- Keep a regression test for two gifts competing for one recipient; add a
  PostgreSQL integration concurrency test when an integration test harness is
  available.
