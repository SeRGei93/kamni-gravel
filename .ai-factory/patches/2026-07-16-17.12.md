# Patch: Prevent stale random manual-gift assignments

## Problem

Parallel owner random assignments could both read an empty recipient and the
later generic update could overwrite the first one. The admin including-awarded
path also observed a current result without locking it, so the result could be
invalidated before the gift update. In Mini App, a mutation for one gift
invalidated the request version of a mutation for another gift and could skip
the completed action's refresh.

## Changes

- Added a narrow initial-recipient repository contract and a transaction that
  locks an unassigned manual gift, validates and locks recipient eligibility,
  then performs a compare-and-set update without requiring approval.
- Locked the current result row in the admin including-awarded transaction;
  DNF remains eligible without a result and a disqualified participant remains
  rejected.
- Serialized all My Prizes mutations and disabled every manual-gift action
  during the active request, including synchronous duplicate callbacks.
- Corrected the README eligibility contract for manual recipient assignment.

## Tests

- Added command and sqlmock regressions for the owner claim conflict and the
  result-row eligibility lock.
- Added a My Prizes regression with two gift cards: the second mutation is
  rejected while the first completes and refreshes the snapshot.
